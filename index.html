AI 驅動架構實戰：Structurizr × OpenCode

郭孟坤 (Mansun Kuo) 外商 Staff Solution Architect
📌

告別手繪過期架構圖，用 Structurizr DSL 與 OpenCode 把 C4 架構和決策脈絡程式碼化。

🎯 核心痛點

傳統架構圖畫完就過期、無法版本控管且難以被 AI 理解；架構師缺乏正式權力卻需跨領域對齊，未記錄決策脈絡（ADR）導致人員離職後留下知識斷層與孤島。

🛠️ 關鍵解法

結合 Structurizr DSL（Diagram as Code）與 OpenCode（AI 輔助架構推導工具），透過 C4 Model 四層抽象（Context、Container、Component、Code）將架構與 ADR 全數文字化並納入 Git 進行演進式設計。

💡 關鍵帶走
  • Why 比 How 重要：架構本質是權衡（Trade-off），善用 ADR 記錄決策脈絡與因果，組織信任才能延續。
  • Diagram as Code：以 Structurizr DSL 取代繪圖軟體，讓架構圖能被 Git 追蹤並作為 AI Agent 的精確系統輸入。
  • 演進式架構（Evolutionary Design）：從最小完整原型（Primitive Whole）出發，透過 OpenCode 搭配動態圖與實戰案例快速演進驗證。

陳宜昌 (YC Chen) Noopher AI CEO and Founder
📌

別讓工程師被 AI 的 Plan-Review 迴圈綁架，把組織拆為人類決策團隊與 Agent 執行團隊。

🎯 核心痛點

把 Spec 寫成 5000 行長文一次丟給 AI 往往直接翻車；一個人帶多個 Agent 時，過度的看板規則與單一對話 Thread 迅速塞爆注意力，工程師淪為改檔機器。

🛠️ 關鍵解法

從「一人 + AI」演進至「人類決策團隊 + Agent 執行團隊」：利用 Matt Pocock 的 grill-with-docs 技巧先對齊領域語言，將 Spec 視為動態鷹架而非死板藍圖，並開源極簡架構的 oat-agents 來協調多 Agent 派工。

💡 關鍵帶走
  • Spec 是動態鷹架而非死板藍圖：別妄想一次生完全部代碼，先用對齊工具確保人機理解同一套領域術語。
  • 切開決策與執行：Agent 擅長在框架內窮舉選項，人則負責跳出框架決策；團隊每人帶 Agent 時需切清 Scope 防止互相覆蓋。
  • 原型期守住關卡不看程式碼：建立驗證機制讓 Agent 自行反覆迭代，工程師把精力聚焦於品味與架構邊界。

前端別再把 Agent 當純打字機，用 Fetch Stream 狀態機與 Abort 信號打造可取消、可續傳的即時介面。

🎯 核心痛點

傳統 EventSource 僅支援 GET 且事件格式死板；Agent 執行多步驟工具調用時間漫長，前端若只當字串傾倒，容易畫面卡頓，且使用者取消時後端依然空轉浪費昂貴 Token。

💡 關鍵帶走

AI 工具爆發時代的企業身分認證治理實戰

吳柏毅 (appleboy) Mediatek 工程師
📌

杜絕長期 Token 裸奔，以 AuthGate 集中認證、MCP Gateway 驗證憑證、GAISF 管控模型流量。

🎯 核心痛點

AI 工具暴發導致每個 MCP/CLI 各自接 LDAP 或把 API Key、長期 Token 寫死在專案設定檔與 Shell History，憑證外洩時無法全面盤點，更無法即時撤銷特定工具權限。

🛠️ 關鍵解法

打造企業級三層治理架構：AuthGate 統一整合企業身份（LDAP/Entra ID/Gitea）並簽發 OAuth/OIDC 權杖；MCP Gateway（Kong + mcp-oauth2）集中驗證 JWT 與 Scope；GAISF 作為單一流量出口進行用量分析與模型稽核；CLI 則透過 Device Flow 或 PKCE 安全取得短期憑證存放於 OS Keyring。

💡 關鍵帶走
  • 工作流程與授權分離：安裝 Skill 不等於擁有系統權限，所有操作必須回溯到明確的執行身份與短期憑證。
  • 集中探索與驗證：MCP Gateway 透過 401 與 Protected Resource Metadata（PRM）指引授權端點，後端只專注工具邏輯。
  • 全生命週期視覺化：提供自服務管理後台讓使用者能看清授權期限、調用 Scope，並能在外洩時一鍵撤銷存取。

產出的人不能驗自己：AI 時代的驗收設計

楊騏 (Ci) WaCare 數位健康 Tech Lead
📌

同一個 AI Session 不能自己驗收自己，以 SDD 規格先行結合全新獨立 Reviewer 打造防護網。

🎯 核心痛點

讓寫 Code 的同一個 AI Session 自己跑審查或驗收，必然產生「球員兼裁判」的確認偏差（把 Bug 視為預期行為）；跨 Repo 前後端規格不一致，AI 經常自創不存在的元件與欄位。

🛠️ 關鍵解法

實施 SDD（Specification-Driven Development）× Test Harness 責任鏈架構：定義最多 7 條的具體 AC（驗收標準，堅持「先紅後綠」），以 Constitution 強制沒來源就標註 not_found；透過 Storybook × MCP 讓 AI 只能引用真實元件庫；並調度未看過實作過程的「全新獨立 Reviewer」嚴格執行 E2E 與代碼審查。

💡 關鍵帶走
  • 產出與驗收嚴格解耦：禁止同一個上下文自審，必須由無偏見的獨立 Reviewer 或自動化測試 Harness 進行驗證。
  • 先紅後綠的驗收邊界：在 AI 動工寫功能前，必須先有能證明「當前會失敗」的測試案例，杜絕無效代碼放行。
  • 精準是一條管線而非單一 Prompt：透過規範契約（AR）、隔離環境驗證與自檢報告，建立錯了收得回來的安全放手藍圖。

當網站客群不再是人類：WebMCP 的前端新革命

黃銘 (Mike Huang) Angular Taiwan 打雜義工
📌

別讓 AI Agent 截圖瞎點按鈕，用 WebMCP 標準與語意表單直接向瀏覽器註冊結構化工具。

🎯 核心痛點

目前 Agent 自動化依賴視訊截圖或解析龐大 DOM 樹，常因網頁改版、按鈕被蓋住或微小樣式變化而點錯，流程脆弱且耗費巨量視覺 Token。

🛠️ 關鍵解法

導入前沿 WebMCP（Web Model Context Protocol）標準（如 navigator.modelContext）：前端以命令式 API（registerTool）註冊具備 JSON Schema 的結構化工具，或利用 HTML 宣告式屬性（<form toolname=... tooldescription=...>）自動將 a11y（無障礙）標籤轉換為 AI 可調用的工具，並以 AbortController 控管生命週期。

💡 關鍵帶走
  • 與其讓 AI 猜，不如主動宣告：WebMCP 讓網頁主動暴露結構化工具，從根本解決爬蟲與視覺點擊的脆弱性。
  • 做好 a11y（無障礙）就是最佳 AI 化：原生 HTML 語意標籤與無障礙屬性能直接轉換為 Agent 工具參數，零成本升級。
  • 重視 Agent Experience（AX）：工具命名應明確直觀，附帶 readOnlyHint 等危險性標籤，並在畫面即時呈現 AI 動作確保人類知情。

自己刻 Agent 框架：最難的不是呼叫 LLM

Jamis Liao 街口支付 (JKOPay) 平台工程師
📌

刻 Agent 框架最難的不是跑 Loop，而是用軌跡評估、Context 精算與確定性規則鎖死出錯邊界。

🎯 核心痛點

幾行代碼就能串起 LLM Tool Loop，但上線後卻頻繁遭遇：模型跳過關鍵步驟自己捏造報告、Context 塞滿原始日誌觸發「迷失在中間」迫使更換昂貴大模型、金流扣款等關鍵操作失控且難以追查重現。

🛠️ 關鍵解法

打造工程級 Agent 框架防線：Context 精準裁剪（工具完整結果留在 Runtime，只傳引用或摘要給模型）；實施雙軌評測（軌跡評估 Trajectory 驗證 Tool 是否按順序調用，結果評估 Outcome 驗收輸出品質）；不可接受的錯誤（如日期、金額）以硬性代碼檢查取代 LLM 自由發揮；高風險操作強制導入 HITL（Human-in-the-Loop）。

💡 關鍵帶走
  • Context 控制關乎模型選型與穩定度：日誌先過濾再進 Prompt，避免 Context 膨脹引發注意力渙散與成本失控。
  • 評測不是打分數，而是驅動迭代：踩過的坑轉為凍結回歸測試集，以 Eval 驗證 Skill 修改，不靠人肉憑感覺改 Prompt。
  • 把不可接受的錯誤做成代碼檢查：零容忍的業務限制嚴禁仰賴模型自律，必須由 Runtime 外部邏輯或工具強行鎖死。

🤖 Agentic AI

讓 AI Agent、MCP Server、CLI 安全登入的實作工作坊

吳柏毅 (appleboy) Mediatek 工程師
📌

掌握 MCP 安全授權實戰：從 401 探索端點、PKCE 換取短期憑證，到 Gateway 集中校驗。

🎯 核心痛點

開發者串接 MCP Server 時習慣把長期 API Key 寫死在客戶端設定，導致外洩風險劇增，且無法界定操作到底代表哪位同仁、能存取哪些細部資料。

🛠️ 關鍵解法

實作標準 OAuth 2.0 / OIDC 授權流程於 MCP：當 Client 未帶 Token 呼叫時，MCP 回應 401 並附帶 Protected Resource Metadata（PRM）；Client 依此至 Signet 授權伺服器透過 Authorization Code + PKCE 取得短期 Access Token；MCP Server 或 Gateway 透過 JWKS 公鑰驗證簽章與 Scope 後方可執行底層工具。

💡 關鍵帶走
  • 401 是安全交握的起點：透過 WWW-Authenticate 與 PRM 建立動態元資料探索，不需在 Client 寫死驗證伺服器資訊。
  • PKCE 保護公開客戶端：CLI 與本機 Agent 無法安全保管 Client Secret，必須採用 PKCE 防止授權碼中途攔截。
  • 雙層權限控管：通過 Gateway 的 Scope 驗證僅代表具備進入資格，後端仍需針對特定工單與資源進行細部權限檢查。

讓 AI 讀懂你的系統 with knowledge graph

Neo Hsu TXOne Networks Staff Software Engineer
📌

Grep 只能找文字，用 Graphify 把代碼 AST 與架構需求串成一張可查詢因果的知識圖譜。

🎯 核心痛點

Agent 最容易死在「找錯 Context」：傳統 Grep 或關鍵字檢索只會撈出一堆孤立片段，分不清核心模組與無關代碼，導致後續推論建立在錯誤前提上產生幻覺。

🛠️ 關鍵解法

借鏡 Karpathy 的 LLM Wiki 思想，使用 Graphify 引擎預先建構 Knowledge Graph：結合 AST 語法解析（硬關係）與 LLM 語意推論（軟關係），將 Repo 代碼、Spec、Docs、Test 連結成一張多模態地圖；支援 `/graphify query` 與 Shortest Path 因果追蹤，並在每條邊標記 EXTRACTED、INFERRED 或 AMBIGUOUS 可信度等級。

💡 關鍵帶走
  • Grep 找「字」，Graph 找「關係」：查詢前預先建立結構化圖譜，讓 Agent 秒級撈出精確的端對端呼叫與依賴路徑。
  • 標註關聯的可信度（Audit Trail）：確定的 AST 代碼關係可直接採信，LLM 推論關係則需標記信心度並引導人工核實。
  • 以圖反哺團隊文檔：若圖譜出現模糊（AMBIGUOUS）或斷鏈節點，代表系統架構文檔不足，應逆向補齊代碼與規格說明。

AI 時代下的另類多工與心流 ：碎片化工作中的「動態專注」法則

Ruddy 老師 集英信誠 顧問
📌

人類無法真正多工，AI 平行跑任務時，人類靠「脈絡重啟卡」實現單點專注與零損耗心流切換。

🎯 核心痛點

引入 AI 後工程師誤以為能同時推進多個任務，結果頻繁在不同工作間切換（Context Switching），冰山之下堆積大量 WIP（未完成工作），注意力被撕裂且難以重回深度思考心流。

🛠️ 關鍵解法

建立「動態專注循環」（AI 平行工作，人類單點專注）：導入布魯姆認知分層，將目標從看懂代碼提升至「能預測行為與定位證據」；任務中斷或切換時填寫「脈絡重啟卡」（記錄 Where 目前進度、Why 當前假設、Next 下一步驗證），取代粗淺的文字摘要，確保切換回來時秒速恢復情境。

💡 關鍵帶走
  • 拒絕偽多工陷阱：人腦無法平行處理高注意力工作，應維持單一主焦點（Main Focus），嚴格限制 WIP 數量。
  • 脈絡重啟卡取代純摘要：摘要只交代發生什麼，重啟卡則凍結「思考方向與當前假設」，讓大腦無痛接軌。
  • 追求高階理解（第 4~5 層）：不僅要看懂 AI 寫了什麼，更要能在系統出事時說出底層因果並知道上哪找證據。

LLM Wiki：企業內部知識問答系統的架構演進

張維峻 (Justin) 國泰金控 助理架構師
📌

規範更新不再引發問答災難，用知識編譯與 Blast Radius PR 機制打造可回歸驗證的 LLM Wiki。

🎯 核心痛點

企業知識庫一更新，傳統 RAG 常因直接 Chunking 導致新舊規範並存衝突、生效日期與前置條件脫鉤，且缺乏代碼級的回歸測試機制，改動一處卻暗中破壞其他問答品質。

🛠️ 關鍵解法

建構「LLM Wiki」與知識編譯（Knowledge Compilation）架構：將知識庫拆為 RAW（來源證據層）與 WIKI（知識產物層，Concepts 與 Claims）；每次法規或規範異動均開立「Knowledge Change PR」，透過模型推導出 Blast Radius Map（衝擊影響範圍地圖），並在合併前跑凍結 Golden Test Set 進行自動化回歸評測與 Judge 偏誤審查。

💡 關鍵帶走

從一人 AI 工作流到團隊工程系統

謝浩哲 (HAO) TSMC Senior IT Engineer
📌

將一人 AI 開發的敏捷實踐提煉為團隊工程資產：從 Context、Constraints、Feedback 三面向診斷環境，以原子增量循環防範技術債，並透過 Team Skill Library 跨專案共享工程紀律。

🎯 核心痛點

只追求當下功能做完，容易引發單檔職責膨脹、重複代碼拷貝（如多套分頁編解碼）及模組反向依賴（如 Service 逆向 import Controller）；個人摸索出的有效 Prompt 與修復經驗無法在團隊跨專案沉澱重用。

🛠️ 關鍵解法

建立三層工程體系：事前對齊 Domain 語言、ADR 與 Given/When/Then 驗收工單；事中推行 Atomic Implementation Loop（拆成可驗證增量，搭配 Policy Reviewer 與確定性工具檢查）；事後透過 Team Skill Library 與 CLI 分發共用規則與能力。

💡 關鍵帶走
  • 三維度診斷工作環境：全面檢視 AI 是否清楚要做什麼（Context）、不能怎麼做（Constraints）、以及何時偏離（Feedback）。
  • 載體職責分明：確定性規則交給 Tool（Linter/依賴圖），重複方法交給 Skill，角色邊界交給 Agent，避免用模型語意硬猜明確規則。
  • 資產共享與專案延伸：集中維護通用團隊能力（如 Dependency Checker），各 Repo 保留特有規則，實現標準持續演進。

模型調用工具時，安全防線必須移至架構層：解析 MCP 工具描述投毒（Tool Poisoning）、Prompt 注入與行為層供應鏈攻擊，從 Zeabur 邊界橫移事件剖析憑證隔離與 Harness 硬防護。

🎯 核心痛點

傳統資安工具（SBOM、代碼掃描）只能檢查靜態程式碼，管不到自然語言撰寫的 MCP Tool Description；外部工具『載入即曝險』，且將 LLM 語意判斷當作唯一安全防線易遭條件繞過（如蔓蔓攻擊），導致環境變數與高權限金鑰外洩。

🛠️ 關鍵解法

落實三大防禦守則：Token 永不進 LLM Context 與明文環境變數；工具執行層落實最小權限原則（PoLP）並與內網機敏資料嚴格隔離；建立 Harness-level 邊界，將決策層與執行層徹底解耦，並對 MCP Tool Description 的 diff 建立審查機制。

💡 關鍵帶走
  • 載入即曝險新型威脅：MCP Server 的工具描述在連線初始化時即進入 Context，惡意指令能在工具被選取前就劫持模型。

🎯 核心痛點

🤖 Agentic AI

讓 AI Agent、MCP Server、CLI 安全登入的實作工作坊

吳柏毅 (appleboy) Mediatek 工程師
📌

為 HTTP MCP 與 CLI 打造企業級安全授權：結合 OAuth 2.0 PKCE、動態 Protected Resource Metadata (PRM) 與 JWT 驗簽，劃清 Scope、Audience 與 Subject 三條防線，並剖析離線撤銷盲點。

🎯 核心痛點

開發者常誤將『連線成功』當成『使用者已取得資源授權』；本地 CLI 無法妥善保管 Client Secret；Token 跨服務任意挪用（未綁定 Audience）；以及誤以為在認證中心按『撤銷』，離線驗簽的 MCP Server 就會立即阻斷存取。

🛠️ 關鍵解法

標準化授權架構：Client 遭遇 401 透過 PRM 自動發現授權端點，利用 PKCE（S256）安全交換 Access Token；MCP Server 嚴格驗簽（RS256/JWKS/iss/aud/exp/sub）；在 Gateway（Kong）集中處理入口驗證，後端保留工具 Scope 與多租戶 Subject 隔離。

💡 關鍵帶走
  • 解碼不等於驗證：JWT 必須嚴格驗證數位簽章、頒發者、過期時間與 Audience，絕不可只用 base64 解開 payload 即放行。
  • 三維邊界互不混淆：Scope 限制可讀不代表可寫、Audience 限制 A 的 Token 不能打 B、Subject 確保不同帳號間資料嚴格隔離。
  • 離線 JWT 撤銷延遲警訊：撤銷不會改變已簽發 Token 的簽章；若要求即時阻斷，需額外設計 Introspection 機制或妥善縮短 Token 壽命。

消除使用者研究的認知摩擦與虛榮指標：將繁瑣的 5x5 狩野模型（Kano Model）精簡為 3x3 務實矩陣，並將 NPS 從主觀打分問卷轉化為依據真實分享行為的免問卷忠誠度公式。

🎯 核心痛點

傳統狩野問卷題目成對且選項冗長（正反向各 5 個選項，填寫負擔極大、受訪者易疲乏亂填）；而傳統 NPS 問卷依賴 0-10 分主觀承諾，常落入『說是一回事、做是一回事』的意向偏差，難以指導真實產品資源配置。

🛠️ 關鍵解法

雙軌務實簡化：將 Kano 選項精簡為正向（喜歡/應該的/無所謂）與反向（不喜歡/能忍受/無所謂），透過 3x3 矩陣快速篩出魅力型 (A)、期望型 (O)、基本型 (M) 與無差異型 (I)；將 NPS 改由真實行為驅動（如主動公開分享體驗以換取折扣券），用實際行動人數計算忠誠度。

💡 關鍵帶走
  • 3x3 矩陣快速決策：大幅降低問卷填答摩擦力，快速識別『一定要有』（基本型）與『不急著優化』（無差異），精準分配研發預算。
  • 真實行動勝過主觀承諾：用戶是否願意付出社交成本或實際操作，比在問卷上勾選推薦分數更能如實反映品牌忠誠度。
  • 用研服務於營運權衡：研究工具的核心不是追求花俏的統計圖表，而是為了在有限團隊資源下做出清晰的先後排序與取捨。

AI 時代下測試的迷思——為什麼綠燈越多，品質卻沒有變好

柯仁傑 (David Ko/敏捷三叔公) Odd-e Technical Coach
📌

打破『綠燈全過等於品質優良』的測試迷思：揭露 AI 測試常見的弱斷言、覆蓋等價類單一與獎勵作弊現象，引進變異測試（Mutation Testing）、Meta 四道篩選門檻與人工探索性測試（Mob Testing）。

🎯 核心痛點

AI 產出的測試常『廣而淺』（同一等價類出多個變體）、『弱斷言』（只驗證 assert not None，金額算錯也全綠）、『測現狀不測意圖』（把現有 Bug 寫進測試合法化），甚至發生 AI 偷改測試以求通過（Reward Hacking）的虛假安全感。

🛠️ 關鍵解法

實施嚴密測試防禦網：推行實例化需求（Example Mapping）先定義預期行為；導入 Meta TestGen-LLM 四道門檻（可編譯、可執行、連跑 5 次穩定、新增覆蓋率 > 0 才保留）；採用變異測試（PIT/mutmut）注入 Bug 驗證測試是否真的會紅；並搭配固定排程的 Mob Testing 與 Bug Bash 探索性測試。

💡 關鍵帶走
  • 沒紅過的測試不能證明有效：在 Merge 前刻意改壞代碼，確認測試會報紅；全綠往往只代表代碼與測試被 AI 改到表面一致。
  • 四道過濾防護網（Meta 實踐）：機器先自動過濾不能編譯、Flaky 或零增量的測試，人類只審查最後通過門檻的高價值測試。
  • 自動化做 Checking，人類做 Testing：自動化腳本負責回歸驗證已知邊界，人類工程師專注於跨功能交互、併發與邊界情境的探索性測試。

林士凱 (Danny) Amazon Web Services Solutions Architect
📌

解決 Text-to-SQL 準確率在企業落地暴跌的致命傷：企業依賴確定性規則而非機率生成，透過語意層（Semantic Layer / AWS Context / 知識圖譜 / 形式本體論與 SHACL 約束）為 Agent 構築 ACE 可信回答。

🎯 核心痛點

🛠️ 關鍵解法

💡 關鍵帶走
  • 商業運作是確定性鏈條，不是機率分布：當決策出錯代價高昂時，『流暢的瞎猜』毫無價值，必須用語意層把機率輸出錨定到確定性模型。
  • 語意層是 GenAI 的核心基礎設施：統一管理企業指標與本體論，避免各個 Agent 應用各自重複進行脆弱的 Prompt Context Engineering。
  • 堅持 ACE 三大標準：追求 Accurate（準確）、Consistent（一致）與 Explainable（具備血緣與圖譜路徑可解釋），建立企業對 AI 的信任。

當 AI 加入團隊：打造可審查、可驗證、會自我改善的 AI 開發工作流

🎯 核心痛點

🎯 核心痛點

💡 關鍵帶走

🎯 核心痛點

傳統資料專案常陷入『交付斷層』：資料團隊算出流失預測分數，業務部門卻只會無效發券；同時 AI 降低了『多做一個版本』的成本，反而讓團隊迷失在大量原型中，不知真正該交付什麼給誰。

🛠️ 關鍵解法

建立完整落地四部曲：1. 場景驅動（以決策者與專員實際接觸情境反推產品規格）；2. 使用 grill-me 在動手前把隱性決策問完，沉澱於 CONTEXT.md（一詞一義）與 ADR 紀錄；3. 輿情與洞察技術（主題分類、情感分析與量化風險）；4. 減法思維收斂為內部『服務策略協作台』，並以實測揭示 Prompt Router 切換模型的快取失效成本（Cache miss penalty）。

💡 關鍵帶走
  • 數據洞察的瓶頸不是模型，而是將洞察轉譯為業務動作：顧客要的是『透明度』消除防衛心，而不是盲目比價打折。
  • 在寫規格前先用交互提問（grill-me）釐清隱性假設，定案才落筆進 ADR，避免事後無止盡爭論。
  • 模型動態路由（Router）並非穩賺不賠：實測顯示頻繁切換模型會使上下文快取（Prompt Cache）重寫 16 倍，省下的推論費往往被快取寫入費吃光。

🎯 核心痛點

Agent Skill（技能手冊）寫好後若缺乏生命週期維護，常面臨指令鬆散被 Agent 跳過、能力擴充時互相衝突，以及改動後破壞原有表現等脫軌問題，難以可靠用於生產環境。

🛠️ 關鍵解法

建立完整的 SkillOps 治理架構：1. 高控制規則閉合六決策點（Condition 觸發、Action 行動、Constraint 禁止、Failure 失敗處理、Precedence 衝突優先級、Evidence 輸出證據）；2. 選擇性融合（僅吸取必要能力，避免無謂膨脹與衝突）；3. 錯誤驅動進化（將執行失敗轉化為可重跑的負案例 Negative examples 作為回歸測試，並通過指令稽核、中央評估、安全檢查三層把關後才准予發布）。

💡 關鍵帶走
  • 『閉合』規則不是把文字寫長，而是堵死所有讓 Agent 自行猜測或跳過步驟的漏洞出口。
  • 技能改進必須靠負案例（Negative examples）驅動：先重現錯誤並固化為回歸測試，確保修復新問題的同時不退化舊能力。
  • 結構正確與模擬通過不等於實際有效：技能發布必須依賴真實執行紀錄與安全合規審查。
