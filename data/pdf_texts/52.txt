09 · 階段 3｜Lint
第一道：depguard 擋直接依賴
.golangci.yml 節錄（module 路徑縮寫為 <module>）
depguard:
rules:
application-production:
list-mode: strict
files:
- "${base-path}/internal/application/**/*.go"
allow:
- $gostd
- <module>/internal/domain
- <module>/internal/pagination
handler-production:
deny:
- pkg: <module>/internal/infrastructure
desc: handlers must depend on application ports, …
list-mode: strict
白名單：沒列的都擋。Application 直接 import persistence，
不在清單就擋下。
desc:
deny 規則的 desc 會出現在違規訊息裡，就是修正提示；白
名單只會說「不在清單」。
nolintlint: require-explanation
用 //nolint 關規則，必須寫明原因並指定 linter，不能默默放
寬。
只看直接 import
只檢查指定檔案的直接依賴，不宣稱已覆蓋整條路徑。
違規訊息寫得好，就不必再補 Prompt。

14 · 階段 4｜PR 流程
為什麼每次發 PR，總是沒照 template 走？
範本只是預填文字
沒有任何東西驗證它有沒有被照著填。
Agent 常用 CLI 或 API 建 PR
網頁上的範本自動帶入，不一定會發生。
Git hook 管不到
PR 描述不在 git 裡，這一關只能放在 CI。
示意：CI 檢查 PR 描述

exit 1
建立／更新 PR
→
CI 檢查段落
→
Agent 依輸出補齊
設成 required check 後，沒補齊就不能合併。
範本是提醒，CI 檢查才是驗收。

15 · 階段 4｜三層防線
三層防線：Agent 自己跑、Git hook、CI
1 · 主動
Agent 自己跑
• 同一個入口：make verify
• 工具版本、環境、掃描範圍要明確
• 回饋最快，直接讀輸出修正
2 · 自動
Git hook
• commit／push 時自動執行
• 可用 --no-verify 繞過，不算強制
• 用 core.hooksPath 或 lefthook 安
裝
3 · 強制
CI＋保護設定
• 對待合併版本重驗
• Required checks、必要 Review、
bypass 權限
• skipped 或 neutral 不等於成功
規則、測試、CI 與豁免清單的修改要另行審查；CODEOWNERS 要搭配強制生效的保護設定。
Hook 負責攔下，CI 負責把關。
